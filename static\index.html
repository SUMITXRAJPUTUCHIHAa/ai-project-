🎓 Academic Defense & System Architecture

📌 Project Overview & Problem Statement

Problem Statement

Prospective university applicants struggle with fragmented admission portals, ambiguous scholarship cutoffs, and delay-prone manual helpdesks. Generic chatbots fail because they hallucinate tuition figures or regulatory refund rules.

Our Solution

A production-grade, hybrid admission intelligence platform combining deterministic rule processing (Rule Engine v2.4) with BM25-retrieval grounded RAG over official institutional datasets, powered by Groq Cloud’s openai/gpt-oss-120b model.

🗄️ Database Entities & Dual-Write Architecture

1. chat_logs

Records every interaction: id, session_id, message, response, intent, confidence, provider, timestamp.

2. custom_rules

Admin-configurable rules: id, pattern, intent, reply, confidence, active, created_at.

3. escalations

Logged whenever confidence is low: id, session_id, user_query, status, priority, created_at.

🎯 Top 5 Examiner Questions & Model Answers

Q1: Why did you not rely entirely on an LLM like ChatGPT?
Model Answer: Admission and fee policies require legal accuracy. LLMs can hallucinate numerical fees, scholarship percentages, or refund terms. By using a hybrid architecture, our deterministic Rule Engine handles statutory policies with 100% precision and sub-5ms latency, while the Groq LLM with BM25 grounding only handles unmapped conversational queries.
Q2: How does your BM25 retrieval grounding work?
Model Answer: We partition official LPU admission documents into 13 curated chunks covering eligibility, fees, hostels, and UGC refund guidelines. When a user asks an unmapped query, BM25 computes token-frequency and inverse-document-frequency relevance, extracts the top-k passages, and injects them into the system prompt with strict negative constraints ("answer only from provided facts; if not found, state clearly").
Q3: How is data persisted and what happens if Firebase is offline?
Model Answer: We implemented a resilient dual-write architecture. Primary storage is embedded SQLite (fully functional offline with zero cloud dependency). Asynchronous sync pushes chat logs, custom rules, and escalations to Firebase Firestore when cloud service account credentials exist on disk.
Q4: How did you test and validate system quality?
Model Answer: We engineered an automated test suite with 110 unit, integration, and UI smoke tests across 7 test modules (API hardening, UI smoke, Firebase CRUD, AI engine RAG, end-to-end chat, rule recognition), achieving a 99.2% intent recognition rate.
Q5: What are the security measures in place?
Model Answer: API inputs are bound to 500 characters to prevent buffer and token exhaustion; parameterized SQL queries prevent SQL injection; API keys are isolated via environment variables (`.env`); and sensitive credentials are excluded from client bundles.
